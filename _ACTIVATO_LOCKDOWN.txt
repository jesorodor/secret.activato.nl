ACTIVATO SECRET — FEATURE LOCKDOWN PATCH (v3)
==============================================

Drop these files into your repo root at the SAME paths (they overwrite the
existing files). Then COMMIT + PUSH to the branch your Docker build pulls,
and rebuild. The Docker build pulls from your fork, so uncommitted changes
will NOT appear in the running app.

WHAT CHANGED
------------
1. FILE UPLOAD — removed (UI gone + API returns 403)
2. IP / CIDR RESTRICTION — removed (UI gone + API forces null)
3. BURN-AFTER-TIME — removed (UI gone + API rejects true)
4. MAX VIEWS — locked to 1 (UI hidden + API enforced)

5. SECURITY SECTION — stripped to password protection only
   No expiration control, no max-views, no IP, no burn, no "remember settings"
   header shown. Only the optional password toggle remains. If the instance
   disables password protection, the card renders nothing.

6. NEW IN v3 — EXPIRATION IS NOW ADMIN-CONTROLLED (not hard-locked)
   - Users see NO expiration choice anywhere.
   - The value used for every secret is the instance's
     "Default secret expiration" setting, which YOU set in the admin panel.
   - The server IGNORES any expiration value sent by the client and always
     applies the admin default. This means:
       * You can change it any time from the admin login — takes effect
         immediately for new secrets, no rebuild needed.
       * Users cannot influence or even see it.
   - Default if you never touch it: 72 hours (3 days).
   Files: api/routes/secrets.ts (server override),
          api/validations/secrets.ts + api/lib/constants.ts (accept standard
          values again instead of only 3 days).

   HOW TO CHANGE IT AS ADMIN:
   Log in as admin -> Instance / Settings -> "Default secret expiration"
   (value is in HOURS: 72 = 3 days, 168 = 7 days, 24 = 1 day, etc.)
   Or via env var on the container: HEMMELIG_DEFAULT_SECRET_EXPIRATION=72

WHY BOTH FRONTEND AND BACKEND
-----------------------------
Frontend edits only hide controls; the backend changes make the policy real
and unbypassable via direct API calls. For expiration specifically, the server
forces the admin default regardless of what any client sends.

VERIFIED
--------
- Frontend production build (vite build) completes successfully.
- Touched files typecheck clean (repo ships with some unrelated pre-existing
  type warnings; the Docker build does not gate on them).

DEPLOY
------
    git add -A
    git commit -m "Activato lockdown v3: admin-controlled expiration, user sees nothing"
    git push origin <your-build-branch>

Then on prod:
    cd /opt/secret-activato
    docker compose build --no-cache
    docker compose up -d --force-recreate

NOTE
----
Changing the default expiration later does NOT require a rebuild — it's a live
admin setting. Rebuild is only needed to apply THIS code patch the first time.
